## Why

Teachers already record daily observations per student (`teacher/daily-reports`: focus entries, KSS observable checklists, evidence text and media), but the term report built from them (`teacher/student-reports`) is a free-text AI paragraph with no scores and no structure. Parents expect the same report they know from the KSS readiness assessment in PPDB (`iqrolife` → `dashboard/assessments`): an overall score, a band, scores per education focus and per indicator, a radar chart, and recommendations. Teachers also need to adjust the report in Word and hand parents a final file, and today there is no way to upload or publish one. The parent report endpoints also leak data: any parent can read any student's report, including drafts.

## What Changes

- Student reports become structured documents stored in `student_reports.content` (jsonb), modelled on the PPDB assessment report: identity, attendance summary, the level of each education focus and indicator on the PAUD scale BB / MB / BSH / BSB, a radar chart, narrative per focus, recommendations, and teacher notes.
- Levels are suggested by backend code from published daily reports in the period, never by AI: each behaviour gets a level from the number of weeks with evidence (1–2 weeks MB, 3–5 BSH, 6+ with recent evidence BSB; no evidence = "Belum terlihat", not scored), indicators get the most frequent behaviour level when at least half their behaviours have evidence, and the homeroom teacher confirms or changes every indicator level (with a reason when changing) before the report can be finalized. A first version that reused PPDB's frequency-to-Likert scores was replaced because it ranked children by how often boxes were ticked rather than by what they can do.
- Two templates: `ASSESSMENT` for classes that have active KSS indicators (SSA, SSB), and `NARRATIVE` for classes without them (KB for now). NARRATIVE reports have narrative per focus, attendance and notes, but no levels.
- Reports are tied to an academic year and a period of one of three types: **term** (triwulan, 3 months, internal for teachers), **semester** (6 months, the official report for parents) and **year**. A report has one row per student, academic year, period type and period number, with a `DRAFT → FINAL → PUBLISHED` lifecycle; only semester and year reports can be published. Behaviour thresholds scale with the number of weeks in the period, and a semester report shows the levels of its term reports as progress. Regenerating is only allowed in DRAFT, and it keeps the narratives the teacher already wrote.
- Narratives are filled first by the coding agent, through two backend CLI scripts: one exports the computed source data for a class and term, and one imports narratives. Gemini generation stays available and writes to the same fields. Every report records its `generation_source` (`AGENT`, `GEMINI`, `MANUAL`).
- Teachers edit the report on the web, and download it as PDF (rendered in the browser like the PPDB report) and as DOCX (generated by the backend, editable in Word).
- Teachers upload final PDF/DOCX files to a report and publish the report to parents. Publishing notifies every linked parent.
- **BREAKING (parent API):** parents can only read reports of their own children, and only PUBLISHED ones. The current `/parent/reports` page is replaced by "Rapor Anak", which shows the web report and the published files, including for KB students.
- Small hardening: the Gemini API key moves from the URL query to the `x-goog-api-key` header.

## Capabilities

### New Capabilities
- `student-report-generation`: Computing a structured report for a student and term from published daily reports (scoring rules, templates, attendance), regenerating drafts, and filling narratives through the agent CLI or Gemini.
- `student-report-editing-export`: Report lifecycle (DRAFT/FINAL/PUBLISHED), web editing of content, and PDF/DOCX export.
- `student-report-publication`: Teacher upload of final files, publish/unpublish, parent notification, and the parent "Rapor Anak" view with ownership checks.

### Modified Capabilities
(none — `daily-class-report-crud`, `evidence-media-upload` and `student-parent-mapping` keep their requirements. This change only reads them or calls them as a new consumer.)

## Impact

- **kss-backend** (NestJS + TypeORM): migration for `student_reports` (add `academic_year_id`, `term`, `period_start`, `period_end`, `template`, `content` jsonb, `generation_source`, `finalized_at`, `published_at`; unique student + year + term), new `student_report_files` table, a scoring service, an export/import CLI (`npm run student-reports:export-source`, `npm run student-reports:import-narratives`), a DOCX export endpoint (new dependency `docx`), file upload through the existing Cloudinary service, a publish notification, and parent ownership checks on all read endpoints.
- **kss-frontend**: rework of `teacher/student-reports` (list per class and term, generate, report editor, PDF/DOCX download, file upload and publish), a shared report view component ported from `iqrolife/components/assessment` (level scale and radar), and a "Rapor Anak" parent page replacing the KB block.
- **Data**: existing `student_reports` rows keep their text content as a legacy narrative and stay visible to teachers. They are not shown to parents until they are regenerated and published.
- **AGENTS.md**: document the two new backend scripts.
